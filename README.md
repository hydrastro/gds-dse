# rtl2gds-study

A repository for controlled RTL-to-GDSII experiments across designs, PDKs, flow
configurations and routing seeds with LibreLane. It answers one question: **how
reliable is design space exploration on open flows?** The study runs a suite of
four cryptographic cores (AES, SHA-256, ChaCha, PRINCE) on three open PDKs
(sky130A, gf180mcuD, ihp-sg13g2). Your ASCON can join as a fifth design.

The repository records reproducibility inputs: the LibreLane commit, the PDK versions it pins,
the four RTL repositories (as submodules), every knob name/type/value (against a
snapshot of LibreLane's own variables), the per-PDK baseline values (copied from
each PDK's own LibreLane config, see [docs/pdk-values.md](docs/pdk-values.md)) and
every campaign's inputs (hashed at `prepare`). Actual RTL and physical-flow validation must still be performed on your machine.

## Start with unchanged RTL and shared experiments

Use the [updated runbook](docs/running-study.md) for installation, CPU limits,
clock bring-up, small pilots and data collection. AES, SHA-256, ChaCha and PRINCE
remain unchanged upstream submodules; their existing top modules are the
benchmarks. General flow variants are shared across designs.

The safe starting preset uses two threads per flow and one flow at a time.
After entering the pinned Nix shell and validating RTL, prepare a single smoke run:

```bash
python3 scripts/study.py prepare --experiment experiments/suite/smoke.json --designs aes --label aes-smoke-001
python3 scripts/study.py run --label aes-smoke-001 --machine-id desktop
```

The shared `pilot-baseline.json` schedules ten seeds per design. The optional
`pilot-2x2.json` schedules ten seeds for density 60/70 x synthesis AREA 0/DELAY 1:
40 flows with `--designs aes`, or 160 with all four designs, on SKY130. Use
`--pdks` to select other platforms after their baselines work. All selections
are frozen into the manifest. Existing large suite/stage plans remain optional.

The [fix notes](docs/project-review.md) explain calibration completeness,
tie-aware ranking, failed transfers and conservative pooling checks. Slack-derived
Fmax/area-delay metrics are disabled. `dse_reliability.csv` now describes
within-sample selection stability, not probability of a true winner.

## 1. Clone and set up

The archive already contains the Git metadata with all five submodules registered
at their pinned commits (LibreLane and the four cores). Commit once (step 0 above),
then push it to your own remote if you want. On another machine:

```bash
git clone YOUR_STUDY_URL rtl2gds-study && cd rtl2gds-study
git submodule update --init      # LibreLane + the designs; LibreLane's own test-data submodules are not needed
```

To add ASCON as a fifth design:

```bash
git submodule add YOUR_ASCON_GITHUB_URL designs/ascon
git -C designs/ascon checkout --detach YOUR_ASCON_COMMIT
```

Then fill `configs/designs/ascon/design.json` as in section 2 and add `"ascon"` to
the `designs` list of the plans (`configs/plans/suite-*.json`) and suite experiments.
Re-run the calibration for ASCON (a calibration experiment with `"designs": ["ascon"]`)
and regenerate the plans.

`.gitmodules` stores URLs and paths. The pinned commits are Git entries in the
parent repository, not SHA fields in `.gitmodules`.

## 2. Design manifests (and adding ASCON)

The four suite manifests (`configs/designs/{aes,sha256,chacha,prince}/design.json`)
are complete. Each uses the core's 32-bit register-interface wrapper as top (about 76
I/O, so pin count is similar across designs), the source list from the core's own
FuseSoC `.core` file, and the shared SDC. Run their upstream functional tests and check elaboration/synthesis in your pinned environment. Their `clock_period_ns` (25 ns) is only a fallback:
the calibrated per-PDK reference in `pdks/<pdk>.json` takes precedence.

For ASCON, edit `configs/designs/ascon/design.json`: replace `top`, `clock_port` and
the ordered `sources` list, and set includes, defines and parameters. Keep `rtl_root`
as `designs/ascon`.

Path rules:

* `rtl_root` and `sdc` are relative to the study repository root.
* `sources` and `include_dirs` are relative to `rtl_root`.
* Optional `project_sources` and `project_include_dirs` are relative to the study
  root. Project sources are appended after the RTL source list; list packages
  before modules that use them.
* `additional_input_files` uses study-root-relative paths (or explicit absolute
  paths) for other dependencies that need hashing, such as macro views or Tcl.

Use `wrappers/<design>/` only if the study needs an adaptation wrapper. If you fix
a design itself, commit that change in its source repository and then advance the
submodule pointer here. A parent commit does not commit or publish uncommitted
changes inside a submodule.

All designs share `configs/constraints/single_clock.sdc` (single clock, LibreLane
`base.sdc` semantics, values from each PDK). A design with a different interface
can point `sdc` at its own file.

## 3. Enter the pinned tool environment

Install Nix and configure the binary cache using the
[LibreLane Linux instructions](https://librelane.readthedocs.io/en/stable/installation/nix_installation/installation_linux.html),
then run from the study root:

```bash
nix-shell tools/librelane/shell.nix
librelane --smoke-test
```

There are three version layers: the LibreLane submodule pins the flow source;
its `flake.lock` selects the Nix dependencies; its `librelane/pdk_hashes.yaml`
selects the Ciel PDK builds. PDK downloads are kept in the ignored `pdks/` cache.
The source-level seed adapter is reviewed for the pinned LibreLane commit and
checks the original Tcl script's hash. Updating the flow requires reviewing
that adapter as well as committing the new submodule pointer.

If you already maintain compatible PDK installations, copy
`machine.example.json` to `machine.local.json` and use this shape for each manual
PDK you want to select:

```json
{
  "manual_pdks": {
    "sky130A": {
      "root": "/absolute/path/to/pdk-root",
      "revision": "Actual installed source/build revisions and local changes"
    }
  }
}
```

The root must contain the PDK subdirectory and flow-ready technology/library
views. Manual PDKs are not hashed in full; keep the installation fixed and record
its real revision. Unlisted PDKs continue to use Ciel. Machine paths do not belong
in the shared design manifest; they are captured in each campaign's provenance.

## 4. Understand configuration precedence

The runner merges the following from lowest to highest precedence. Later values
replace earlier values with the same key; arrays are replaced, not concatenated.
Keys starting with `//` are comments and are ignored.

1. `configs/defaults.json` → `flow_overrides`.
2. The selected PDK's `overrides` in `configs/platforms.json`.
3. `configs/designs/<design>/design.json` → `clock_period_ns` and `flow_overrides`.
4. `configs/designs/<design>/pdks/<pdk>.json`, when present.
5. `configs/variants/<variant>.json`.

Layer 4 holds the calibrated reference clock of each design × PDK, written by
`scripts/calibrate_clock.py` (e.g. `configs/designs/aes/pdks/gf180mcuD.json` →
`{"CLOCK_PERIOD": …}`). Layer 2 holds each PDK's own LibreLane defaults, written out
(see [docs/pdk-values.md](docs/pdk-values.md)).

**Relative values.** Any layer can express a value relative to the layers below it:

```json
{"CLOCK_PERIOD": {"$scale": 0.85}, "FP_CORE_UTIL": {"$add": 10},
 "RT_MAX_LAYER": {"$per_pdk": {"sky130A": "met4", "gf180mcuD": "Metal4", "ihp-sg13g2": "Metal4"}}}
```

`$scale` and `$add` apply to the value merged so far, or to the LibreLane default.
So "15% tighter clock" means the same relative change on every PDK even though
each PDK has its own reference period. `$per_pdk` picks a value per PDK (and may
contain the other operators). `{"$of": ["CLOCK_PERIOD", 0.02]}` is 2% of the
*final* merged value of another key (resolved after all layers, so it follows a
scaled clock).

**Validation.** Every key must be a real LibreLane Classic-flow variable at the
pinned commit, with the right JSON type and, for choices, an allowed value.
`prepare` checks this against `configs/librelane_variables.json` and suggests the
right name for typos (e.g. `PL_TIME_DRIVEN` → `PL_TIMING_DRIVEN`). Deprecated
aliases are rejected in favour of the canonical name, so every campaign records
one name per setting. The merged configuration of every job must also satisfy
`config_constraints` in `configs/study.json` (for example
`PL_TARGET_DENSITY_PCT >= FP_CORE_UTIL + 5`). If not, `prepare` stops before
creating anything. After moving the LibreLane submodule, regenerate the snapshot
inside the Nix shell with `python3 scripts/librelane_vars.py` and commit it.

**Constraints (SDC).** The study SDC takes every number from the configuration.
LibreLane variables (`IO_DELAY_CONSTRAINT`, `OUTPUT_CAP_LOAD`,
`CLOCK_UNCERTAINTY_CONSTRAINT`, `CLOCK_TRANSITION_CONSTRAINT`,
`TIME_DERATING_CONSTRAINT`, `MAX_*_CONSTRAINT`) reach it through `$::env(...)`.
Values LibreLane has no variable for are `STUDY_SDC_*` keys in any layer (input
transition, hold uncertainty, minimum I/O delay). They are substituted into
`@STUDY_SDC_…@` placeholders at `prepare` and are never passed to LibreLane.
Each distinct rendered SDC is saved and hashed under `inputs/constraints/`. A
placeholder without a value, or a `STUDY_SDC_*` value the template does not use,
is an error.

Top/source identity, PDK/library identity, SDC paths, threads and the routing seed
are managed explicitly from the manifests/experiment; override layers cannot
replace those fields. This prevents a variant from quietly changing the design
under test. Each job has `config.json` with the fully merged input and
`config_origins.json` identifying the winning layer for ordinary flow settings.
LibreLane subsequently writes its own fully resolved configuration in the run.

**Study settings.** `configs/study.json` holds everything that used to be
hardcoded: the LibreLane pin, the reviewed `grt.tcl` hash and capacity
perturbation (0) of the seeded step, threads, `parallel_jobs`, default timeout,
kill grace, PDK cache directory, default `order_seed`, a job-count guard, extra
flow arguments, tool-version probes, RTL hash extensions, config constraints,
which checks are required for `study_checks_pass`, the metric columns exported
to `runs.csv`, summary fields and all analysis settings. It is frozen into each
campaign, and `collect`/`analyze` use the frozen copy.

## 5. Use experiment files to describe batches

`experiments/ascon-pilot.json` contains one C0 run for each PDK:

```json
{
  "phase": "pilot",
  "designs": ["ascon"],
  "pdks": ["sky130A", "gf180mcuD", "ihp-sg13g2"],
  "configs": ["C0"],
  "seeds": [1],
  "repeat": 1,
  "stop_after": null,
  "order_seed": 20261015
}
```

Run it with:

```bash
python3 scripts/study.py prepare --experiment experiments/ascon-pilot.json --label ascon-pilot-001
python3 scripts/study.py run --label ascon-pilot-001 --machine-id desktop-i7
```

`prepare` expands the design × PDK × variant × seed × repeat grid and snapshots
inputs. It assigns a unique `campaign_id` and saves the shuffled job IDs in
`schedule.json`, with a checksum in `manifest.json`. `run` reads that saved order
and executes the jobs (one at a time unless `parallel_jobs` > 1). The label must be
new for `prepare`.

**Resuming after a crash, power loss or Ctrl-C:** run the same command again
(`run --label <same label>`). Finished jobs (`completed`, `flow_error`, `timeout`,
`launcher_error`) are never recomputed, so failures stay recorded as results.
Jobs that never finished (`running`, left by a dead runner, or `interrupted` by
Ctrl-C) run again from the start of the flow. Their partial files are moved,
not deleted, to `jobs/<id>/aborted/<n>/`, and the new attempt lists them in
`previous_attempts` (`runs.csv` → `previous_unfinished_attempts`). A rerun of
the same seed replaces an attempt that produced no result, so it does not add a
duplicate sample. Use `--no-retry-incomplete` to leave unfinished jobs alone.
A lock file (`runner.lock`) stops a second runner from working on the same
campaign. The OS releases it automatically if the runner or the server dies.

Leave `order_seed` at its default unless a new experiment deliberately needs a
different execution order. The same value can be reused across designs and
campaigns. Select the routing `seeds` once in the experiment definition; the
runner assigns them automatically. `order_seed` controls scheduling only, while
`seeds` controls the initial global router. Neither is the simulation stimulus
seed. Reusing routing seed numbers across configurations, PDKs and designs is
allowed; duplicate entries in one `seeds` list are rejected.

`run` automatically creates or refreshes `runs.csv`, `metrics_long.csv` and
`summary.csv` after the batch finishes, including ordinary errors or Ctrl-C.
No manual transcription is needed. After a power loss or forced kill, or to
refresh tables while reviewing historical results, use:

```bash
python3 scripts/study.py collect --label ascon-pilot-001
python3 scripts/study.py summarize --label ascon-pilot-001
```

The optional `--machine-id` gives the execution host a stable readable name;
omitting it uses the hostname. Each invocation automatically records CPU model,
logical CPUs, CPU affinity where available, host-visible RAM, OS, free disk space,
Python and tool provenance. Each attempt includes its machine snapshot and a
reference to that invocation's `environment-*.json`. RAM describes the host as
seen by the process, not necessarily a cluster allocation or container limit.
Record any allocated resources and time limits in the study protocol as well.

CSV rows include campaign identity, routing seed, `order_seed`, planned schedule
position, execution identity, machine information and configured thread count.
Summary groups are separated by machine ID and thread count as well as design,
PDK and configuration. Files are JSON/CSV, not a SQL database; no service or
database setup is required. Back up the complete campaign separately from Git.

Experiment files may be nested by design: after moving the pilot definition to
`experiments/ascon/pilot.json`, pass that path to `--experiment`. This does not
require changing the runner or any seed values.

When applying this runner update to an existing study, finish existing campaigns
with their original scripts or retain that Git revision. Commit the updated files
before preparing a fresh formal campaign. The new runner requires a newly saved
schedule and frozen input hashes prevent silently changing old campaigns. Old
results remain readable with `collect` and `summarize`; unavailable historical
schedule/machine fields stay empty rather than being guessed.

The package includes synthesis-only, same-seed repeat, baseline and density
experiment files. Their exact commands and acceptance checks are in the
[experiment guide](docs/experiment-guide.md).

`phase: pilot` allows uncommitted parent/design edits during bring-up and records
their state/hashes. The LibreLane checkout must still match the reviewed pin.
`phase: study` requires a clean, committed parent repository and initialized
submodules at their committed revisions; it rejects repeated identical seeds
and partial flows. It also rechecks repository versions before launching each
job. Commit before `prepare` and keep the recorded revision throughout the
campaign. Both phases reject changes to frozen input/configuration files.

## 6. Generate variants from the knob catalogue

`configs/knobs.json` lists 59 LibreLane settings that make sense to vary
(synthesis, floorplan, placement, resizer, CTS, global/detailed routing,
constraints, antenna), each with levels, an optional continuous range and a
one-line reason. All of them are validated against the pinned variable snapshot.
Knobs that would add a second source of randomness are `opt_in` and blocked
unless a plan sets `"allow_opt_in": true`. The study's noise model is the
initial global-routing seed only, and these knobs would break it:
`RUN_HEURISTIC_DIODE_INSERTION`/`DIODE_ON_PORTS` (LibreLane's `diodes.py` calls
Python `random` without a seed) and `RUN_POST_GRT_*` (they re-run global routing
with the default seed).

```bash
python3 scripts/variants.py list            # catalogue by group (add --all for opt-in knobs)
python3 scripts/variants.py check           # catalogue vs LibreLane snapshot
python3 scripts/variants.py generate configs/plans/stage1-core-knobs.json [--dry-run]
```

A plan chooses a strategy (`ofat`, `factorial`, `lhs` or `list`), knobs (by name,
by `groups`, or `"all"`), optional per-knob `levels`/`ranges` and an `experiment`
block. Generation:

* expands PDK-aware levels: `{"$rows": n}` (n standard-cell row heights → µm per
  PDK), `{"$value": v, "$with": {...}}` (a level with companion settings, e.g. padding
  that also raises density), `{"$of": [...]}` and `{"$scale": x}`;
* adds prerequisites (`requires`: e.g. resizer margins only matter with
  `RUN_POST_CTS_RESIZER_TIMING`) and prints a note for knobs that only act on some
  PDKs (`effective_pdks`, e.g. adder mapping exists only in sky130A);
* merges each variant with the real config layers for every target design × PDK;
* drops variants that violate `config_constraints`, duplicate another variant or
  equal the baseline, listing them with reasons in
  `configs/plans/<name>.generated.json`;
* writes `configs/variants/<name>__*.json` and the experiment file.

Re-running a plan replaces only its own generated files. Commit the results like
hand-written variants. Shipped plans:

| Plan | Strategy | Variants | Jobs (3 PDKs) | Purpose |
|---|---|---|---|---|
| `suite-calibrate` | 8 absolute clock periods per PDK | 8 | 288 (3 seeds, to post-route STA) | Reference clock per design × PDK |
| `stage1-core-knobs` | OFAT: clock, utilisation, density, synthesis strategy, flattening | 10 | 660 (5 seeds) | The prof's starting knobs |
| `stage2-cts-routing` | OFAT: every default CTS, global- and detailed-routing knob | 29 | 1800 (5 seeds) | First expansion |
| `stage3-remaining` | OFAT: every other default knob (stage-1 knobs excluded) | 47 | 1728 (3 seeds) | Complete coverage |
| `confirm-factorial` | Full factorial over the knobs that mattered (edit before use) | 31 as shipped | 3840 (10 seeds) | Effects, interactions, transfer, DSE reliability |
| `explore-lhs` | Latin hypercube, 40 points over 12 knobs | 40 | 1476 (3 seeds) | Response surfaces (optional) |

Only the calibration and stage-1 variants are generated in the shipped repository.
Each later plan writes its variant files when you run `generate` on it.
Job counts are for the 4-design suite on 3 PDKs, including the baseline C0.

Regenerate the plans after changing defaults or design/PDK layers, because
feasibility is checked against them.

**Parallel execution.** `execution.parallel_jobs` in `configs/study.json` (default
1) runs that many flows at once, launched in the saved schedule order. Keep
`parallel_jobs × threads` at or below the physical cores. Each attempt records
`parallel_jobs`. Runtime is only comparable between campaigns with the same
setting and CPU-limit policy. Check repeatability and record resource failures; do not assume resource changes are harmless. On Ctrl-C, every running flow is
stopped and marked `interrupted`.

## 7. Analyse a campaign

```bash
python3 scripts/analyze.py --label core-001
.venv-analysis/bin/python scripts/plot_analysis.py --label core-001
```

This writes `results/<label>/analysis/report.md` plus CSV tables answering six
questions. How large is the seed noise? Which configurations differ from the
baseline beyond it (bootstrap CI + FDR)? How much variance is configuration vs
PDK×configuration vs seed? Which knobs matter? Does the configuration ranking
transfer across PDKs (Kendall τ, regret)? How stable is selection when resampling k seeds per point from the observed data? Every failed run stays in the data: failures appear as
pass fractions, `failure_reason` and `failed_step`, and as feasibility in the
rankings. See the [analysis guide](docs/analysis-guide.md) for how to read each
table, how many seeds you need and the recommended campaign sequence.


```bash

```

## 9. Add another design when ready

```bash
git submodule add YOUR_GITHUB_URL designs/mycore
git -C designs/mycore checkout --detach YOUR_COMMIT
mkdir -p configs/designs/mycore/pdks
cp configs/designs/aes/design.json configs/designs/mycore/design.json
```

Edit the copied manifest's `rtl_root`, `top`, `clock_port`, `sources` and includes
(the shared single-clock SDC works for any single-clock core). Calibrate its clock
using `experiments/suite/calibrate.json --designs mycore` at preparation,
run `calibrate_clock.py --write`, then add it to the plans' `designs` and regenerate.
Commit the additions.
No runner changes are needed. Every run ID includes the design, and summaries
group by design, PDK, configuration, machine, thread count and recorded resource controls. Plots are
separated into design folders.

For two architectures from the same RTL repository, create distinct configuration
directories/experiment design IDs that point to the same submodule with different
parameters. They are distinct experimental designs even when they share a Git pin.

## Validation

```bash
python3 -m unittest discover -s tests -v
```

80 checks cover config precedence, relative operators (`$scale`, `$add`, `$per_pdk`, `$of`), variable/type/choice
validation against the LibreLane snapshot, config constraints, SDC rendering,
multi-design expansion, real temporary Git submodules, changed-input detection,
failed-run/timing collection with failure attribution, frozen ordering, machine
provenance, preserved prior attempts, Ctrl-C, crash resume with archiving, the single-runner lock, parallel execution, catalogue
consistency, OFAT/factorial/LHS generation, matched-corner timing collection, clock
calibration, the calibrated-clock guard for study campaigns, and the analysis. The analysis tests
use synthetic runs with planted effects: real effects must be found, null effects
must stay `no_clear_difference`, reversed rankings must show negative τ and a large
PDK×configuration share, and ties must share bootstrap credit. Resampling reports within-sample agreement, not true-optimum accuracy. No RTL simulation, synthesis or GDSII flow was executed during this update; use the pinned EDA environment for that validation.

The Git behavior follows the [official submodule documentation](https://git-scm.com/book/en/v2/Git-Tools-Submodules).
The reviewed flow is [LibreLane at this commit](https://github.com/librelane/librelane/tree/01ddb25e4424f6f5aaf6b951b14a2b6fdcf737c0).
